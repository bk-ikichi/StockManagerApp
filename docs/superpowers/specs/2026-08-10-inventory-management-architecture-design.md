## 変更履歴（v1 → v2、2026-08-17）

画面一覧の洗い出しから派生したギャップ分析（HTTPS未対応・監視の仕組みなし等）をきっかけに、ホスティング方針を再検討した。

- **ホスティングをVPS（ConoHa→Xserver）からRender（アプリ）＋Neon（DB）に変更**：開発者がプロのエンジニアではなくソロ運用のため、「円建てで安く」より「自分で対処できない障害を起こしにくい」ことを優先する方針に切り替えた。VPSは自由度が高い分、OSパッチ・死活監視・HTTPS証明書更新・DBバックアップをすべて自前で構築・保守する必要があり、未経験者には運用中の事故（気づかないまま長時間ダウンする等）のリスクが実店舗の業務に直結すると判断した。RenderはHTTPS自動付与・基本的な死活監視・OSパッチ不要という形でこれらを肩代わりしてくれる
- 上記に伴い、円建て課金優先の方針は撤回。月額は多少増える（VPS想定900〜1,150円→Render+Neonで7ドル/月程度〜）が、運用リスク低減を優先する
- モノリス構成（フロント/バック分離なし）・セッションベース認証・レイヤー構成・store_id設計など、ホスティング方式に依存しない決定はすべて維持（詳細は各節を参照）
- 開発中のホスティング費用は完全にゼロにする：開発はローカルのDocker Composeのみで行い、VPS/Renderいずれの環境も開発中は常時起動しない（詳細は3章）

## 2. アーキテクチャ

### 2.1 全体構成

**Render（アプリ）＋ Neon（DB）**上で完結する構成とする（2026-08-17変更、旧方針は単一VPS。変更理由はv2変更履歴を参照）。

- **バックエンド**：Spring Boot（Java）によるモノリス構成。マイクロサービス化はしない（変更なし）
- **フロントエンド**：React。ビルド成果物をSpring Bootの静的リソースとして同梱配信する（フロントエンドを別ホストに分離しない＝同一オリジン）。Renderには1つのWebサービス（Dockerイメージ）としてこのモノリスをそのままデプロイする（変更なし）
- **DB**：PostgreSQL。ホスティングはNeon（サーバーレスPostgres）を使う。デフォルトのオートサスペンド（5分無操作でスリープ、復帰は約1秒）はそのまま許容し、無効化のための追加課金はしない（詳細は3.2）
- **コンテナ化（ローカル開発用）**：開発中はDocker Compose（アプリコンテナ＋ローカルPostgreSQLコンテナ）でローカルマシン上のみで完結させる。開発中の課金は発生しない。RenderへのデプロイはDockerイメージのビルド＆pushで行う
- **ファイル保存**：フェーズ7（OCR自動化、MVP後）で納品書PDFの保存が必要になるが、Renderのファイルシステムは揮発性（再デプロイ・再起動で消える）のためVPS前提だった「ローカルディスク保存」案は使えない。フェーズ7着手前にオブジェクトストレージ（Cloudflare R2等）の採用を検討する（未決事項、6章参照）

検討した他の構成案（不採用）：
- VPS（ConoHa/Xserver等）に単一構成でまとめる案 → 円建て課金・OCR自前運用との相性は良いが、OSパッチ・死活監視・HTTPS証明書・DBバックアップをすべて自前で構築・保守する必要があり、非プロフェッショナルのソロ運用者には事故のリスクが大きいと判断し不採用（2026-08-17）
- フロントエンドをVercel/Netlify等に分離し、バックエンドAPI＋DBのみRender/VPSに置く案 → セッションCookie認証がクロスオリジンになり、SameSite/Safari ITP等の影響を受けやすくなる。この規模のアプリでは分離のメリットが薄いため不採用
- Supabase（DB）＋サーバーレス構成 → 直接接続がIPv6専用、IPv4接続にはプーラー経由が必要でJDBCのプリペアドステートメントキャッシュと相性問題が起きやすい（開発者が過去に実際に遭遇済み）。Neonは同じ問題を踏まずに動作実績があるため不採用

### 2.2 認証

Spring Securityによる**セッションベース認証**を採用する（JWTは不採用）。ホスティングをVPSからRenderに変更した後もこの判断は変わらない（Render上でもモノリス1サービスとして同一オリジンでデプロイするため、前提が崩れていない）。

理由：
- フロントエンド・バックエンドが同一オリジンのため、Cookieベースのセッションで技術的な支障がない
- 単一インスタンス構成のため、JWTが強みを発揮する「複数サービス間でのステートレスな検証」「水平スケーリング時のセッション共有」といった利点が活きない
- v8 10章の「共通アカウント運用（社員・ゲストは使い回し、退職時のみパスワード変更）」との相性が良い。サーバー側セッション管理であれば、パスワード変更時に該当アカウントの全セッションを即座に無効化できる。JWTだと自己完結型トークンのため、同等の即時失効を実現するには追加のブロックリスト等の仕組みが必要になり、この規模には過剰

### 2.3 バッチ処理

発注点・安全在庫の自動再計算（v8 5.3、7章）は、**毎日の確定ボタン押下時に同期的に実行する**。Quartz等の専用ジョブスケジューラは導入しない（新しい非同期基盤を持ち込むより、既存の確定処理イベントに乗せる方がシンプルで、ソロ開発の実装・運用コストを抑えられるため）。

### 2.4 複数店舗対応（データモデルのみ先行）

主要テーブルには初回リリース時点から `store_id` を持たせる。UIとしての複数店舗対応（店舗切替、店舗間移動、新店舗ブートストラップ）はフェーズ6（MVP後）に回すが、**データモデルへの`store_id`付与は初回リリースから行う**。理由：この部分だけは後から追加するとマイグレーション・データ移行のコストが高く、最初から持たせるコストはほぼゼロに近いため。

### 2.5 バックエンドのレイヤー構成・実装規約

以降の全フェーズで、バックエンドは以下の規約に統一する（2026-08-10のフェーズ0計画レビュー時に確定）。

- **レイヤー構成は `mapper → repository → service → controller` の順**とする
  - **mapper**：SQLを直接書くinterface（MyBatisの`@Mapper`インターフェース＋`@Select`/`@Insert`/`@Update`等のSQLアノテーション）。Spring Data JPA／Hibernateのような自動生成クエリ・`@Entity`ベースのORMは使わない
  - **repository**：mapperをラップする層
  - **service**：業務ロジック・トランザクション境界
  - **controller**：HTTPの入出力のみを担当し、業務ロジックを持たない
- **DTOを使用する**：controllerの入出力（リクエスト/レスポンス）は、永続化用のドメインオブジェクト（mapperが返す型）とは別のDTOクラスを介する
- **ドキュメントはすべて日本語で書く**：設計書・仕様書・実装計画など、説明文はすべて日本語で記述する（コード自体の識別子は通常のプログラミング規約に従い英語のままでよい）

この規約はPhase 0（`docs/superpowers/plans/2026-08-10-phase0-infrastructure-auth.md`）以降、すべてのバックエンド実装計画に適用する。

## 3. インフラ・コスト（2026-08-17改訂）

### 3.1 ホスティング選定

開発中とMVP以降の本番運用で構成を分ける。

| フェーズ | 構成 | 理由 |
|---|---|---|
| 開発中（〜10/15） | **ローカルマシン＋Docker Compose**（無料） | クラウド環境を常時起動する必要がない。既存のdocker-compose.yml（アプリコンテナ＋PostgreSQLコンテナ）をローカルで動かすだけで開発が完結する |
| 本番運用（10/15〜） | **Render**（Webサービス、Starterプラン）＋ **Neon**（Postgres） | HTTPS自動付与・基本的な死活監視・OSパッチ不要など、非プロフェッショナルのソロ運用者が事故りにくい構成を優先。Renderは1つのDockerイメージ（モノリス）をそのままデプロイできる |

検討した他の選択肢：
- VPS（ConoHa／Xserver／さくらのVPS等）：円建て課金・OCR自前運用との相性は良いが、HTTPS証明書・死活監視・OSパッチ・DBバックアップを自前で構築・保守する必要があり、ソロ・非プロフェッショナル運用にはリスクが大きいため不採用（詳細はv2変更履歴）
- Render無料プラン：15分無操作でスリープし、復帰に数十秒かかる。実店舗が17〜21時に毎日使う業務フローとの相性が悪いため、有料のStarterプラン（常時起動）を採用
- Supabase（DB）：3.2参照
- AWS Lightsail／Vultr／DigitalOcean：ドル建て課金かつAWSは学習コストも高く、Renderと比べて非プロフェッショナル運用向けのメリットがないため不採用

### 3.2 DB選定：Neon

Neon（サーバーレスPostgres）を採用する。

- デフォルトのオートサスペンド（5分無操作でスリープ、復帰約1秒）はそのまま許容する。無効化（常時起動）も可能だが、最小構成でも月$15〜20程度かかる見込みで、Renderアプリ側が常時起動していればDB側の1秒程度の復帰待ちは実用上ほぼ気にならないため、追加課金はしない
- Supabaseは過去のプロジェクトで採用を試みたが、直接接続がIPv6専用でRender等のIPv4環境から繋がらず、プーラー経由（トランザクションモード）に切り替えるとJDBCのプリペアドステートメントキャッシュと衝突するトラブルに遭遇済み。Neonは同じ問題を踏まずに動作実績があるため採用継続

### 3.3 概算コスト

| 項目 | 月額目安 |
|---|---|
| 開発中（ローカルDocker Compose） | 0円 |
| Render Webサービス（Starterプラン、常時起動） | $7程度 |
| Neon（無料枠の範囲内を想定。超過時は従量課金） | $0〜 |
| **本番運用の合計目安** | **$7〜／月（≒1,000〜1,100円程度、為替により変動）** |

ドル建て課金になるため為替変動の影響を受ける点は許容する（3.1参照、運用リスク低減を優先）。LINE通知は無料枠内（v8 9章で確認済み）。DBバックアップはNeonの機能（ポイントインタイムリカバリ等）を活用する方針とし、独自のバックアップ機構は当面構築しない（詳細は6章）。

## 6. 未解決・今後の検討事項

- v8 13章に残る未決事項（テスト稼働モード中の異常値検知基準、データバックアップ・障害時対応、正確な商品点数、業者側の休配日）は本ドキュメントのスコープ外。フェーズ実装時に順次対応する
- **業者側の休配日確認（v8 13章No.4）**：リードタイム計算（5.6）・発注点計算（5.3）の前提を左右するため、フェーズ3着手前にユーザー自身が業者へ確認する必要がある（実装では解決できない外部確認タスク）
- **【B1・設計方針決定、フェーズ4で実装】社員／ゲストのパスワードリセット手段**：v8 10章は「退職者が出た場合のみパスワードを変更する」としているが、現状の`AccountService.changePassword`は本人が現在のパスワードを知っている前提の実装のみで、MGが強制的にリセットする手段（API・画面）がない。以下の方針で設計する（2026-08-17決定）。
  - 実装時期はフェーズ4（権限仕上げ）：機能面が一通り揃ってから権限・セキュリティ関連の機能をまとめて追加する方針のため、フェーズ0では対応しない
  - リセット方式：MGが対象アカウント（STAFF/GUEST）に任意の新パスワードを直接入力して保存する（現場ですぐ本人に口頭で伝えられるようにするため）。システムによるランダム仮パスワード発行＋次回ログイン時強制変更（ADMINの初回ログインと同じ`must_change_password`方式）は採用しない（共通アカウントの「使い回し」運用とは相性が悪いため）
  - 現在のパスワードの入力は不要（MGが強制的に上書きするため、本人確認は不要）
  - 実装上の注意点：これがアプリ初のロールベース認可（ADMIN限定）エンドポイントになる。現状の`SecurityConfig`はログイン済みか否かのみを判定しており、ロールごとのアクセス制御はまだ存在しない。フェーズ4で`@PreAuthorize`または`SecurityFilterChain`での`hasRole("ADMIN")`指定を初めて導入する
  - 誰が・いつ・誰のパスワードをリセットしたかの記録は、A3（修正履歴／監査ログテーブル）に乗せる（フェーズ2でテーブルが先に作られているため、フェーズ4時点では既に存在する）
