## 2. アーキテクチャ

### 2.1 全体構成

単一VPS上で完結する構成とする。

- **バックエンド**：Spring Boot（Java）によるモノリス構成。マイクロサービス化はしない
- **フロントエンド**：React。ビルド成果物をSpring Bootの静的リソースとして同梱配信する（フロントエンドを別ホストに分離しない＝同一オリジン）
- **DB**：PostgreSQL
- **コンテナ化**：Docker Compose（アプリコンテナ＋DBコンテナ）。目的は環境再現性・バックアップ（DBボリュームのスナップショット）のしやすさであり、**コスト削減が目的ではない**（VPSの料金はDockerの有無に関わらずCPU/メモリ/ディスクの割当量で決まる）
- **ファイル保存**：納品書PDF等はVPSのローカルディスクに保存する（この規模でオブジェクトストレージ導入は過剰と判断）

検討した他の構成案（不採用）：
- フロントエンドをVercel/Netlify等に分離し、バックエンドAPI＋DBのみVPSに置く案 → CORSや2箇所デプロイの管理コストが増える割に、この規模でのメリットが薄いため不採用
- Supabase等のマネージドBaaS＋サーバーレス構成 → v8で決定済みのJava/Spring技術方針、および将来のTesseract OCR自前サーバー運用（常駐プロセスが必要）と噛み合わないため不採用

### 2.2 認証

Spring Securityによる**セッションベース認証**を採用する（JWTは不採用）。

理由：
- フロントエンド・バックエンドが同一オリジンのため、Cookieベースのセッションで技術的な支障がない
- 単一VPS・単一インスタンス構成のため、JWTが強みを発揮する「複数サービス間でのステートレスな検証」「水平スケーリング時のセッション共有」といった利点が活きない
- v8 10章の「共通アカウント運用（社員・ゲストは使い回し、退職時のみパスワード変更）」との相性が良い。サーバー側セッション管理であれば、パスワード変更時に該当アカウントの全セッションを即座に無効化できる。JWTだと自己完結型トークンのため、同等の即時失効を実現するには追加のブロックリスト等の仕組みが必要になり、この規模には過剰

### 2.3 バッチ処理

発注点・安全在庫の自動再計算（v8 5.3、7章）は、**毎日の確定ボタン押下時に同期的に実行する**。Quartz等の専用ジョブスケジューラは導入しない（新しい非同期基盤を持ち込むより、既存の確定処理イベントに乗せる方がシンプルで、ソロ開発の実装・運用コストを抑えられるため）。

### 2.4 複数店舗対応（データモデルのみ先行）

主要テーブルには初回リリース時点から `store_id` を持たせる。UIとしての複数店舗対応（店舗切替、店舗間移動、新店舗ブートストラップ）はフェーズ6（MVP後）に回すが、**データモデルへの`store_id`付与は初回リリースから行う**。理由：この部分だけは後から追加するとマイグレーション・データ移行のコストが高く、最初から持たせるコストはほぼゼロに近いため。

### 2.5 バックエンドのレイヤー構成・実装規約

以降の全フェーズで、バックエンドは以下の規約に統一する（2026-08-10のフェーズ0計画レビュー時に確定）。

- **レイヤー構成は `mapper → repository → service → controller` の順**とする
  - **mapper**：SQLを直接書くinterface（MyBatisの`@Mapper`インターフェース＋`@Select`/`@Insert`/`@Update`等のSQLアノテーション）。Spring Data JPA／Hibernateのような自動生成クエリ・`@Entity`ベースのORMは使わない
  - **repository**：mapperをラップする層
  - **service**：業務ロジック・トランザクション境界
  - **controller**：HTTPの入出力のみを担当し、業務ロジックを持たない
- **DTOを使用する**：controllerの入出力（リクエスト/レスポンス）は、永続化用のドメインオブジェクト（mapperが返す型）とは別のDTOクラスを介する
- **ドキュメントはすべて日本語で書く**：設計書・仕様書・実装計画など、説明文はすべて日本語で記述する（コード自体の識別子は通常のプログラミング規約に従い英語のままでよい）

この規約はPhase 0（`docs/superpowers/plans/2026-08-10-phase0-infrastructure-auth.md`）以降、すべてのバックエンド実装計画に適用する。

## 3. インフラ・コスト

### 3.1 VPS選定

2段階でVPSを使い分ける。

| フェーズ | プロバイダ | 理由 |
|---|---|---|
| 開発中（〜10/15） | **ConoHa VPS**（2GBクラス、時間課金対応） | サーバー構成を試行錯誤する開発初期は、時間課金で無駄なく安く試せる柔軟性を優先 |
| 本番運用（10/15〜） | **Xserver VPS**（2GBクラス、長期契約） | 国内シェアNo.1・CPU性能に優れ、長期契約時が最安値クラス。実店舗で使う本番環境として実績・性能を優先 |

検討した他の選択肢：
- さくらのVPS：老舗で実績豊富だが、Xserver/ConoHaと比べるとやや割高（月1,594円程度、石狩リージョン）
- AWS Lightsail（2GBプラン、$10/月）：ドル建て課金による為替変動リスク、AWSの他サービスを使う誘惑によるコスト増リスク、IAM/VPC等の学習コストの高さから不採用。信頼性は高いが今回のコスト最優先方針とは合わない
- Vultr / DigitalOcean（海外）：ドル建て、国内向け実運用としては優先度低

### 3.2 概算コスト

| 時期 | 月額目安 |
|---|---|
| 開発中（ConoHa 2GB、時間課金） | 〜1,150円程度 |
| 本番運用（Xserver 2GB、長期契約） | 900円〜（契約期間による） |
| OCR導入後（フェーズ7、4GBクラスへ増強想定） | 3,500〜4,000円程度 |

ドメイン・SSL（Let's Encrypt）は任意・低コスト、LINE通知は無料枠内（v8 9章で確認済み）。バックアップはVPSプロバイダの追加オプション（月200〜400円程度）を任意で検討。

## 4. 初回リリース（MVP）のスコープ判断

以下は「作らない／後回しにする」という明示的な判断。理由も含めて記録する。

| 機能 | 判断 | 理由 |
|---|---|---|
| OCR自動化（v8 2章） | フェーズ7（MVP後）に延期 | v8 2.5で手入力ルートが既に必須機能として設計されているため、OCRなしでも業務は回せる。OCR精度チューニングは工数が読みにくく、10/15という締切のリスクになるため |
| フェア管理機能（v8 8章） | フェーズ8（MVP後）に延期 | 現在開催中のフェアがあるが、発注点ロジックは通常商品と共通（v8 8章に既に明記）のため、専用機能なしでも通常商品として手動運用すれば実害はない |
| 複数店舗対応のUI（v8 11章、4.4） | フェーズ6（MVP後、11月新店舗オープンに向けて着手） | 新店舗は11月オープンのため、10/15時点では店舗切替・店舗間移動を使う相手が存在しない。データモデルのみ先行対応済み（2.4参照） |
| LINE通知（v8 9章） | フェーズ9（最後） | v8時点で既に「優先度：最低」と明記されている |
